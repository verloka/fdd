One outcome.
The whole path to it.

A flow is more than an endpoint or a class. It follows a user action, event or background job through to an observable outcome, including validations, failures, side effects and asynchronous continuations.

It can span UI, APIs, a database and a queue. The contract connects these parts so a local change preserves the larger intent.

02 / Setup

Install without the extra stack

FDD consists of templates and three agent skills. No Python, MCP server or separate framework is needed. Download the repository archive and extract it.

With PowerShell

On Windows, open PowerShell 5.1+ or 7+ in the kit directory and point it at your project:

PowerShell
.\install.ps1 -Project 'C:\Projects\MyProject' -Agent Both

Use -Agent Codex or -Agent Claude for a single tool. Add -DryRun to preview the changes first.

Your files are preserved. The installer preserves existing instructions and flow documents. If it finds a conflict with customized skills, it cancels the installation.

Manually, on any platform

  1. Copy templates/flows/index.md and _template.md into docs/flows/. Do not overwrite existing files.
  2. Copy skills/<name>/SKILL.md for each of the three skills into .agents/skills/<name>/ for Codex and/or .claude/skills/<name>/ for Claude Code.
  3. Append templates/policies/AGENTS.block.md to AGENTS.md, and for Claude, append CLAUDE.block.md to CLAUDE.md. Keep existing instructions.
What gets installed
project/
├── AGENTS.md / CLAUDE.md
├── docs/flows/
│   ├── index.md
│   └── _template.md
├── .agents/skills/       # Codex
└── .claude/skills/       # Claude Code

Both tools share the documents in docs/flows/.

03 / First run

Start with what already works

In an existing project, invoke $flow-bootstrap in Codex or /flow-bootstrap in Claude Code. Then scope the work to a small, related part of the system:

Agent prompt
Discover the end-to-end business flows in this repository.
Inventory user and background entry points in docs/flows/index.md.
Trace the first 3–5 related flows, recording evidence
and coverage gaps. Keep new flow documents in Draft status.
Do not change application code. Continue in batches from the index.

The agent will inspect code and tests, connect entry points to outcomes and record unknowns. A partial scan must explicitly state what remains uninspected.

Discovered

A candidate is identified, but its path has not been traced.

Draft

The flow is documented from code. It needs human review.

Active

A human has approved the contract. Its requirements must be preserved.

Approval is yours. The agent never promotes Draft to Active on its own. Observed code behavior is not proof that the behavior is correct.
04 / In practice

A normal request. Clear consequences.

After installation, describe changes as you normally would. Project instructions route the agent to the right skill; explicit commands are optional.

FDD skills and agent commands
TaskCodexClaude Code
Discover flows$flow-bootstrap/flow-bootstrap
Change behavior$flow-develop/flow-develop
Review regressions$flow-verify/flow-verify

Example: add booking cancellation

  1. Find the affected flow and dependent flows: availability, notifications and payments.
  2. Before coding, update only the requirements you intend to change. Preserve the remaining clauses of Active contracts.
  3. Change the implementation and run relevant tests. Check reverse dependencies and side effects.
  4. Link scenarios to real tests. If a test is missing, explicitly mark the scenario [untested].
05 / Format

A contract you can read

One Markdown file per business outcome. Start with the full template; below is a shortened illustration, not an approved contract.

docs/flows/booking-create.mdDraft

Create a booking

Trigger → outcome
Customer submits a form → confirmed booking or explicit rejection.
Main path
Validate the tenant and service, resolve an employee, check availability, create the booking and initiate a notification.
Invariant
An employee cannot have overlapping confirmed bookings.
Rejection
If the slot is occupied, reject the request without creating a booking.
Scenario
Given an available slot, When a customer submits valid data, Then a booking is created. [untested]
Unknowns
Transaction boundaries, retries and notification failure behavior need verification.

Include inputs, outputs, validations, side effects, dependencies and implementation references. Full example: Create Booking.

06 / Principles

What holds it together

01

The business outcome sets the boundary

The document covers the whole path, even when it crosses several services.

02

Contracts change deliberately

Do not rewrite an Active document to justify a bug. Change only the agreed behavior.

03

Gaps stay visible

Uninspected entry points, unknown conditions and untested scenarios stay visible, even when a batch is done.

04

The process stays lightweight

Changes that cannot affect business behavior do not need FDD analysis. No separate validator or BDD framework is required.
