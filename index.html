Сначала поток.
Потом код.

Описывайте то, что должно произойти с точки зрения бизнеса. Сохраняйте этот смысл, когда меняете код вместе с AI-агентом.

Один результат.
Весь путь к нему.

Поток — не отдельный endpoint или класс. Это путь от действия пользователя, события или фоновой задачи до наблюдаемого результата: с проверками, ошибками, побочными эффектами и асинхронными продолжениями.

Он может проходить через UI, API, базу данных и очередь. Контракт связывает эти части, чтобы локальное изменение не потеряло общий смысл.

02 / Подготовка

Установка без лишнего стека

FDD — это шаблоны и три навыка для агента. Python, MCP-сервер и отдельный фреймворк не нужны. Скачайте архив репозитория и распакуйте его.

Через PowerShell

В Windows откройте PowerShell 5.1+ или 7+ в папке набора и укажите ваш проект:

PowerShell
.\install.ps1 -Project 'C:\Projects\MyProject' -Agent Both

Используйте -Agent Codex или -Agent Claude для одного инструмента. Добавьте -DryRun, чтобы сначала увидеть список изменений.

Ваши файлы сохраняются. Установщик сохраняет существующие инструкции и документы потоков, а при конфликте с изменёнными навыками отменяет установку.

Вручную, на любой платформе

  1. Скопируйте templates/flows/index.md и _template.md в docs/flows/. Существующие файлы не заменяйте.
  2. Скопируйте skills/<name>/SKILL.md для каждого из трёх навыков в .agents/skills/<name>/ для Codex и/или .claude/skills/<name>/ для Claude Code.
  3. Добавьте содержимое templates/policies/AGENTS.block.md в AGENTS.md, а для Claude — CLAUDE.block.md в CLAUDE.md. Сохраните прежние инструкции.
Что появится в проекте
project/
├── AGENTS.md / CLAUDE.md
├── docs/flows/
│   ├── index.md
│   └── _template.md
├── .agents/skills/       # Codex
└── .claude/skills/       # Claude Code

Документы в docs/flows/ общие для обоих инструментов.

03 / Первый запуск

Начните с того, что уже работает

В существующем проекте вызовите $flow-bootstrap в Codex или /flow-bootstrap в Claude Code. Затем задайте небольшой связанный участок системы:

Запрос агенту
Найди сквозные бизнес-потоки в этом репозитории.
Составь инвентарь пользовательских и фоновых входных точек
в docs/flows/index.md. Проследи первые 3–5 связанных потоков,
запиши доказательства и пробелы в покрытии.
Оставь новые документы в статусе Draft. Код не меняй.
Продолжай следующими порциями из индекса.

Агент изучит код и тесты, свяжет входные точки с результатами и отметит неизвестное. Частичный обзор должен явно указывать, что ещё не изучено.

Discovered

Кандидат найден, но путь ещё не прослежен.

Draft

Поток описан по коду. Требует проверки человеком.

Active

Человек одобрил контракт. Его требования нужно сохранять.

Одобрение — за вами. Агент не переводит Draft в Active самостоятельно. Наблюдаемое поведение кода ещё не доказывает, что оно правильное.
04 / В работе

Обычный запрос. Явные последствия.

После установки описывайте изменения привычным способом. Инструкции проекта направят агента к нужному навыку; вызывать команды каждый раз необязательно.

Навыки FDD и команды агентов
ЗадачаCodexClaude Code
Найти потоки$flow-bootstrap/flow-bootstrap
Изменить поведение$flow-develop/flow-develop
Проверить регрессии$flow-verify/flow-verify

Например: добавить отмену бронирования

  1. Найдите затронутый поток и зависимые потоки: доступность, уведомления, оплату.
  2. До кода уточните только требования, которые намеренно меняются. Сохраните остальные условия Active-контрактов.
  3. Измените реализацию и запустите релевантные тесты. Проверьте обратные зависимости и побочные эффекты.
  4. Свяжите сценарии с реальными тестами. Если теста нет, явно оставьте [untested].
05 / Формат

Контракт, который можно прочитать

Один Markdown-файл на бизнес-результат. Начните с полного шаблона; ниже — сокращённый пример, а не одобренный контракт.

docs/flows/booking-create.mdDraft

Создание бронирования

Триггер → результат
Клиент отправляет форму → подтверждённая бронь или явный отказ.
Основной путь
Проверить организацию и услугу, подобрать сотрудника, проверить доступность, создать бронь и инициировать уведомление.
Инвариант
У сотрудника не может быть пересекающихся подтверждённых бронирований.
Отказ
Если время занято, отклонить запрос без создания брони.
Сценарий
Given свободное время, When клиент отправляет валидные данные, Then создаётся бронь. [untested]
Неизвестное
Границы транзакции, повторы и поведение при ошибке уведомления требуют проверки.

Добавляйте входные и выходные данные, валидации, побочные эффекты, зависимости и ссылки на реализацию. Полный пример: Create Booking ↗.

06 / Ориентиры

Что держит всё вместе

01

Бизнес-результат задаёт границы

Документ объединяет весь путь, даже если он проходит через несколько сервисов.

02

Контракт меняется осознанно

Не переписывайте Active-документ, чтобы оправдать баг. Меняйте только согласованное поведение.

03

Пробелы остаются видимыми

Неизученные входные точки, неизвестные условия и сценарии без тестов не скрываются за словом «готово».

04

Процесс остаётся лёгким

Для изменений, не влияющих на бизнес-поведение, FDD-анализ не нужен. Отдельный валидатор или BDD-фреймворк не требуется.
