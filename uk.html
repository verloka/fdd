Увесь шлях до нього.

Потік — це не окремий endpoint чи клас. Це шлях від дії користувача, події або фонового завдання до спостережуваного результату: з перевірками, помилками, побічними ефектами й асинхронними продовженнями.

Він може проходити через UI, API, базу даних і чергу. Контракт пов’язує ці частини, щоб локальна зміна зберігала загальний зміст.

02 / Підготовка

Встановлення без зайвого стеку

FDD — це шаблони й три навички для агента. Python, MCP-сервер та окремий фреймворк не потрібні. Завантажте архів репозиторію й розпакуйте його.

Через PowerShell

У Windows відкрийте PowerShell 5.1+ або 7+ у папці набору й укажіть ваш проєкт:

PowerShell
.\install.ps1 -Project 'C:\Projects\MyProject' -Agent Both

Використовуйте -Agent Codex або -Agent Claude для одного інструмента. Додайте -DryRun, щоб спочатку переглянути зміни.

Ваші файли зберігаються. Установник зберігає наявні інструкції та документи потоків, а в разі конфлікту зі зміненими навичками скасовує встановлення.

Вручну, на будь-якій платформі

  1. Скопіюйте templates/flows/index.md і _template.md до docs/flows/. Не замінюйте наявні файли.
  2. Скопіюйте skills/<name>/SKILL.md для кожної з трьох навичок до .agents/skills/<name>/ для Codex та/або .claude/skills/<name>/ для Claude Code.
  3. Додайте вміст templates/policies/AGENTS.block.md до AGENTS.md, а для Claude — CLAUDE.block.md до CLAUDE.md. Збережіть попередні інструкції.
Що з’явиться у проєкті
project/
├── AGENTS.md / CLAUDE.md
├── docs/flows/
│   ├── index.md
│   └── _template.md
├── .agents/skills/       # Codex
└── .claude/skills/       # Claude Code

Документи в docs/flows/ спільні для обох інструментів.

03 / Перший запуск

Почніть із того, що вже працює

У наявному проєкті викличте $flow-bootstrap у Codex або /flow-bootstrap у Claude Code. Потім обмежте роботу невеликою пов’язаною ділянкою системи:

Запит агенту
Знайди наскрізні бізнес-потоки в цьому репозиторії.
Склади перелік користувацьких і фонових точок входу
в docs/flows/index.md. Простеж перші 3–5 пов’язаних потоків,
запиши докази та прогалини в покритті.
Залиш нові документи у статусі Draft. Код не змінюй.
Продовжуй наступними порціями з індексу.

Агент дослідить код і тести, пов’яже точки входу з результатами й позначить невідоме. Частковий огляд має явно вказувати, що ще не досліджено.

Discovered

Кандидата знайдено, але шлях ще не простежено.

Draft

Потік описано за кодом. Потрібна перевірка людиною.

Active

Людина схвалила контракт. Його вимоги потрібно зберігати.

Схвалення — за вами. Агент не переводить Draft в Active самостійно. Спостережувана поведінка коду ще не доводить, що вона правильна.
04 / У роботі

Звичайний запит. Явні наслідки.

Після встановлення описуйте зміни звичним способом. Інструкції проєкту скерують агента до потрібної навички; викликати команди щоразу необов’язково.

Навички FDD та команди агентів
ЗавданняCodexClaude Code
Знайти потоки$flow-bootstrap/flow-bootstrap
Змінити поведінку$flow-develop/flow-develop
Перевірити регресії$flow-verify/flow-verify

Наприклад: додати скасування бронювання

  1. Знайдіть зачеплений потік і залежні потоки: доступність, сповіщення, оплату.
  2. До змін у коді уточніть лише вимоги, які змінюються навмисно. Збережіть решту умов Active-контрактів.
  3. Змініть реалізацію та запустіть відповідні тести. Перевірте зворотні залежності й побічні ефекти.
  4. Пов’яжіть сценарії з реальними тестами. Якщо тесту немає, явно залиште [untested].
05 / Формат

Контракт, який можна прочитати

Один Markdown-файл на бізнес-результат. Почніть із повного шаблону; нижче — скорочений приклад, а не схвалений контракт.

docs/flows/booking-create.mdDraft

Створення бронювання

Тригер → результат
Клієнт надсилає форму → підтверджене бронювання або явна відмова.
Основний шлях
Перевірити організацію та послугу, обрати працівника, перевірити доступність, створити бронювання й ініціювати сповіщення.
Інваріант
Працівник не може мати підтверджених бронювань, що перетинаються.
Відмова
Якщо час зайнятий, відхилити запит без створення бронювання.
Сценарій
Given вільний час, When клієнт надсилає валідні дані, Then створюється бронювання. [untested]
Невідоме
Межі транзакції, повтори й поведінка в разі помилки сповіщення потребують перевірки.

Додавайте вхідні та вихідні дані, валідації, побічні ефекти, залежності й посилання на реалізацію. Повний приклад: Create Booking.

06 / Орієнтири

Що тримає все разом

01

Бізнес-результат задає межі

Документ охоплює весь шлях, навіть якщо він проходить через кілька сервісів.

02

Контракт змінюється усвідомлено

Не переписуйте Active-документ, щоб виправдати баг. Змінюйте лише погоджену поведінку.

03

Прогалини залишаються видимими

Недосліджені точки входу, невідомі умови й сценарії без тестів не ховаються за словом «готово».

04

Процес залишається легким

Для змін, що не впливають на бізнес-поведінку, FDD-аналіз не потрібен. Окремий валідатор чи BDD-фреймворк не потрібний.
